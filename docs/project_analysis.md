# 课题分析：基于数据增强的源代码漏洞检测

## 1. 这个课题究竟在做什么

这个课题的核心不是“单纯生成更多漏洞代码”，也不是“单纯训练一个分类模型”，而是：

**围绕小型开源漏洞检测模型，构建一套由数据增强驱动的迭代优化流程。**

它包含三个相互配合的研究对象：

1. **输入特征怎么变得更适合小模型学习**
   - 原始函数通常很长，直接输入会超过上下文窗口，或者让有效漏洞语义被噪声稀释。
   - 所以需要切片、提纯、融合，得到高信噪比的漏洞相关代码片段。

2. **增强数据怎么真正帮助模型，而不是制造噪声**
   - 数据增强不是离线随机扩增，而是要围绕模型当前的薄弱点做“定向增强”。
   - 当前论文思路里，增强种子来自验证集漏报样本，即 false negatives。

3. **增强后的数据最终服务于什么**
   - 服务于下一轮训练数据构造。
   - 换句话说，增强后的样本不是最终成果，它们是下一轮微调的训练资产。

所以，课题真正的闭环是：

`原始数据 -> 特征提纯/切片 -> 训练小模型 -> 找漏报 -> 定向增强 -> 质量过滤 -> 回灌训练集 -> 再训练`

## 2. 数据增强后干什么

数据增强后的样本，必须至少完成以下动作，才有科研意义：

1. **语法质量控制**
   - 防止增强结果成为无效代码。
   - 当前项目使用 Tree-sitter 做 AST 级过滤。

2. **与原训练样本统一表征**
   - 如果训练入口吃的是切片/精炼后的 `refined_code`，增强样本也应该走同样的特征提取链路。
   - 否则会出现训练分布不一致。

3. **并回训练集**
   - 增强样本必须进入下一轮训练集，而不是只统计生成数量。

4. **驱动下一轮微调**
   - 这一步决定课题究竟是“增强研究”还是“代码生成演示”。

因此，本课题中“数据增强”的真正目的不是扩数据集规模，而是：

**提升下一轮漏洞检测模型在难例上的召回率、平衡精度与泛化能力。**

## 3. 最终是训练开源模型，还是微调

就当前课题和现有代码而言，合理答案是：

**以开源预训练模型为基础，做监督微调，而不是从零训练。**

原因有三点：

1. 课题重点不在于训练更大的模型，而在于：
   - 特征提纯方式是否更好，
   - 数据增强是否更有效，
   - 损失设计是否更适配类别失衡。

2. 从零训练代码模型代价太高
   - 数据量、算力、时间都不匹配大创与论文周期。

3. 论文变量应尽量集中
   - 更合适的做法是固定下游小模型，例如 CodeBERT、GraphCodeBERT、UniXcoder 之类，
   - 将创新集中在切片、增强、反馈回灌和训练策略上。

所以，这个课题的合理任务定义应该是：

> 面向小型开源代码模型，研究如何通过高质量特征切片与定向数据增强，提高源代码漏洞检测性能。

## 4. 课题的核心科学问题

从论文和代码综合看，这个课题至少包含四个核心问题。

### 问题 1：小模型到底吃什么输入最合适

- 原始长函数？
- 静态切片？
- LLM 语义切片？
- 静态切片和语义切片融合结果？

这是“表征构造问题”。

### 问题 2：增强应不应该围绕模型漏报样本做闭环

- 随机增强通常会引入大量无效样本。
- 以验证集 FN 为种子更符合课题目标。

这是“增强触发机制问题”。

### 问题 3：增强样本怎样保证质量

- 只靠 LLM 输出不够。
- 需要语法校验、去重、结构过滤，最好未来还能做语义一致性约束。

这是“增强质量控制问题”。

### 问题 4：类别失衡下怎样稳定训练

- 漏洞检测通常存在正负样本失衡。
- 需要损失层面的适配，如 focal loss、label smoothing、阈值校准。

这是“训练目标适配问题”。

## 5. 现有代码真正对应的研究模块

当前学长代码虽然组织比较散，但研究意图其实比较清楚，可以分成五层。

### 第一层：数据资产准备

- `clean_dataset.py`
- `make_smoke_dataset.py`

职责：清洗原始 PrimeVul 数据，构造训练/验证/测试数据源。

### 第二层：特征提取与切片

- `generate_cpg.py`
- `slice/slice.sc`
- `llm_pre_filter.py`
- `llm_fusion_refine.py`

职责：把长函数变成更适合小模型的漏洞相关片段。

### 第三层：增强生成

- `cot_enhance.py`
- `cwe_enhance.py`
- `cwe_spider.py`
- `config_cot.py`
- `config_cwe.py`

职责：围绕漏报样本生成新的高价值漏洞样本。

### 第四层：增强质量控制与回灌

- `tree_sitter_val.py`
- `merge_dataset.py`

职责：过滤非法增强样本，并构造下一轮训练集。

### 第五层：训练、反馈与消融

- `finetune_lambda_miu.py`
- `ablation.py`
- `feature_ablation.py`
- `data_aug_ablation.py`
- `loss_ablation.py`

职责：微调下游模型、提取漏报样本、验证各模块贡献。

## 6. 这个课题后续最值得突破的点

老师提到“把切片环节从原来的 LLM 切片变为小模型切片”，这其实非常有研究价值。

更准确地说，可以把“切片”拆成两个环节来看：

1. **静态结构切片**
   - 当前是 Joern + 规则 + 双向遍历。
   - 未来可研究更好的 seed 定位与图遍历策略。

2. **语义切片/精炼**
   - 当前主要依赖大模型初筛与融合。
   - 未来可以探索用小模型替代：
     - 序列标注模型，预测哪些行应该保留；
     - 二分类模型，对候选语句/基本块打分；
     - 图模型，对 CPG/PDG 节点做重要性评分；
     - 检索式 reranker，对 Joern 候选片段排序。

因此，“LLM 切片换小模型切片”不应理解为简单删掉 LLM，而应理解为：

> 将当前依赖大模型完成的语义定位与融合任务，替换为一个可训练、成本更低、可复现性更强的小模型模块。

这会自然形成一条新的论文主线：

- 旧方案：`Joern + LLM 初筛 + LLM 融合`
- 新方案：`Joern + 小模型切片器 + 可选轻量融合`

## 7. 迁移与重构原则

为了后续继续做科研，不应该再围绕“脚本名”组织项目，而应该围绕“研究流程节点”组织。

新的组织原则应该是：

1. **统一数据模型**
   - 明确什么是原始样本、静态切片样本、增强样本、训练样本。

2. **统一配置入口**
   - 不能靠每个脚本里改 `RUN_MODE` 和路径字符串。
   - 应该用配置文件统一管理模型、路径、迭代轮次、切片策略、增强参数。

3. **统一阶段接口**
   - 清洗、切片、融合、增强、验证、训练，每个阶段都应有明确输入输出。

4. **为新方法预留替换位点**
   - 特别是切片器、增强器、训练器，都要能替换实现，而不是把逻辑写死在脚本里。

## 8. 本次重构的目标

这次重构不追求一次性把所有科研问题解决，而是先完成“课题落地底座”：

1. 写清楚课题分析和代码映射关系。
2. 建立基于 `uv` 的包化工程结构。
3. 提供统一配置、统一数据模型、统一 CLI。
4. 把现有代码的核心逻辑迁移到新结构中。
5. 为后续替换切片器、扩展模型、增加评估指标预留接口。

## 9. 迁移后的推荐研究主线

后续建议按下面这条线推进：

1. 先固定一个可靠下游基线
   - 例如 CodeBERT 微调。

2. 保持增强闭环不变
   - 这样新论文的变量更聚焦。

3. 把“语义切片器”做成独立模块
   - 当前先保留 `LLMPreFilter + FusionRefine`。
   - 后面可以新增 `SmallModelSlicer` 与之对比。

4. 做严格对比实验
   - 原始长函数
   - Joern 静态切片
   - LLM 切片
   - Joern + LLM 融合
   - Joern + 小模型切片

这条线最容易和当前代码、老师建议以及论文目标接起来。
