# CodeT5 行级切片器迁移方案

## 1. 迁移目标

本次迁移不是让 `CodeT5` 直接替换最终漏洞检测器，而是让它接管“增强链路中的语义切片职责”。

也就是：

`原函数 -> CodeT5 行级切片 -> line_slice -> 增强生成 -> 质量过滤 -> 增强训练集 -> CodeBERT 检测器评估`

这样做的好处是：

1. 创新点更聚焦在“增强数据构造系统”。
2. 能与当前主结构直接对齐。
3. 更容易写成论文中的独立技术贡献。

## 2. 为什么不是直接生成最短代码

本项目里的“切片”仍然定义为：

1. 从原函数中抽取与漏洞相关的代码行。
2. 再将这些行组织成可用的片段。

不是：

1. 理解原代码后自由改写成语义等价的新函数。
2. 也不是追求抽象重写后的最短正确程序。

因此本次 `CodeT5` 方案采用“行级切片序列预测”而不是“自由生成代码片段”。

## 3. 设计原则

### 3.1 保持行级方案

用户已经选择“行级切片器方案”，所以 `CodeT5` 不直接输出代码，而是输出：

1. 原函数中应保留的行号标签
2. 例如：`L003 L004 L005`

### 3.2 弱化幻觉风险

为了借用 `SLICEFORMER` 的核心思想，但又避免一次性重构太多，本次先实现轻量版约束：

1. 输入函数显式编号
2. 目标序列只允许生成行号标签
3. 解码后只保留输入中出现过的合法行号
4. 自动去重、排序、补块平衡

这样可以显著降低直接生成代码时常见的：

1. 幻觉新 token
2. 幻觉新语句
3. 语法块不闭合

## 4. 监督数据与任务定义

监督数据直接复用现有资产：

1. 输入：`func`
2. 监督：`matched_teacher_line_numbers`
3. 辅助先验：`static_line_numbers`
4. 教师来源：优先 `refined_code`

任务形式：

1. 输入：带行号的完整函数文本 + 静态切片提示
2. 输出：行号序列

示意：

输入：

```text
Task: select vulnerability-relevant lines.
Return only line tags separated by spaces.
StaticSliceHints: L003 L004
Function:
L001 int f() {
L002   int a = source();
L003   if (a > 0) {
L004     return a;
L005   }
L006   return 0;
L007 }
```

输出：

```text
L003 L004 L005
```

## 5. 与当前 CodeBERT 行分类切片器的关系

当前 baseline：

1. `CodeBERT`
2. 行级二分类
3. 每一行单独打分

新方案：

1. `CodeT5`
2. 整函数到行序列的 seq2seq
3. 一次性预测整段切片

两者保留并行，后续对比的核心问题包括：

1. `CodeT5` 是否能更好建模跨行依赖
2. `CodeT5` 是否能输出更完整的漏洞上下文块
3. `CodeT5` 生成的 `line_slice` 是否能进一步提升增强数据质量

## 6. 第一阶段实现范围

第一阶段不直接复现 `SLICEFORMER` 全部内容，只先落地最关键的可跑部分：

1. 新增 `src/vulnbooster/codet5_slicer.py`
2. 支持训练 `func -> line tags`
3. 支持预测 `FN -> line_slice`
4. 接入 `scripts/run_small_model_aug_experiment.py`
5. 支持完整跑通一轮增强实验

## 7. 第二阶段可继续借用的论文思想

等第一轮结果出来后，再逐步借用 `SLICEFORMER` 的两个更强思想：

1. 数据流感知预训练式增强
   - 对教师样本做基于 DFG 的语句置换
   - 对变量依赖片段做 span corruption
2. 约束解码
   - 限制输出 token 只能来自行号词表
   - 加入语法块与邻接约束

这两项更适合作为论文里的第二层创新，而不是第一次迁移就全部塞进去。

## 8. 本轮实施顺序

### 8.1 代码

1. 新增 `CodeT5SlicerConfig`
2. 新增 `codet5_slicer.py`
3. 在 CLI 中增加训练/预测入口
4. 在实验脚本中增加 `--slicer-backend codet5`

### 8.2 验证

1. 单元测试校验行号序列格式化与解析
2. 跑本地 `unittest`
3. 跑语法检查

### 8.3 实验

1. 先跑一轮完整 `CodeT5` 后端实验
2. 与当前冻结版 `CodeBERT line_slicer` 结果对比
3. 判断下一步是继续优化切片器，还是联动增强生成器再调一次

## 9. 成功判据

本轮 `CodeT5` 迁移成功，不以“切片器本身 paper 指标”作为唯一标准，而以两层结果共同判断：

1. 切片层
   - 预测行集合质量不低于当前 baseline 太多
   - 空切片率不能过高
2. 增强层
   - 验证保留率稳定
   - 最终检测器在 `Precision / F1 / MCC` 至少一项出现可观提升

如果 `CodeT5` 在切片指标略强但下游增益不明显，说明还需要继续做：

1. 机理感知切片提示
2. 切片结果与生成 prompt 的对齐设计
3. 更强的数据质量层
